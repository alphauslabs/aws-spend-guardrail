# Design

## Context

- The AI guard's prices are `internal/packs/ai/prices.json`, embedded in the binary: 79 Bedrock models, us-east-1, from the AWS Price List API, about 8 KB. It was generated by an ad-hoc script that is not in the repo.
- Config is a versioned document in a per-payer-org dataset (`config_versions`: version primary key, JSON document, published time, note, layout version). The guard reads the latest version every 5 minutes with its reader key, keeps the last valid one in DynamoDB, and alerts on outages (`internal/guard/pull.go`).
- The reader key reaches only `guardrail.<msp>.<payer>.config` today (`schema.GuardCredentials`).
- Jennah limits: Spanner allows 10 MiB per cell; gRPC defaults to 4 MiB per message and no override was found in Jennah; query results are capped per tier and silently cut short, while reads by primary key are not.
- Estimated sizes: AI prices 8 KB today, about 100 KB in several years; EC2 prices about 15 to 30 KB per region for one hourly price per instance type, 300 to 500 KB across all regions.

## Goals / Non-Goals

**Goals:**
- New models and price increases reach every guard without a release.
- A shared table can never loosen protection on its own.
- A layout that holds compute prices without redesign.

**Non-Goals:**
- Price decreases through Jennah (they come with a release or per-org `ai.prices`).
- Fetching prices from AWS inside the guard (it would change behavior without a release, and a lower price would loosen without approval).

## Decisions

### D1. Manifest plus chunks, fetched by key
`guardrail.prices` has two tables:

- `price_versions`: `version` (INT64, primary key), `published_at`, `note`, `layout_version`, and `manifest` (JSON): a list of `{pack, region, sha256, models}`.
- `price_chunks`: `version`, `pack`, `region` (composite primary key), and `document` (JSON): the chunk's prices in the same per-model format as today's table, with `source`, `published`, and `basis`.

The guard reads the latest manifest (one row, ordered by version, limit 1) and fetches each needed chunk by its full primary key, so no read depends on a capped result count. A chunk is capped at 1 MiB at publish time, well under the 4 MiB message limit. A version is immutable, like a config version.

*Alternative:* one row per model. Rejected: a table read becomes a query capped per tier, an update isn't atomic, and history needs extra work.

*Alternative:* one document per version. Rejected for compute: all EC2 regions in one document approach the message limit.

### D2. Only what changed, only what's needed
The guard keeps, per chunk it uses, the manifest hash it holds. It downloads a chunk only when the hash differs, for packs it runs (the AI pack: `ai/us-east-1`), and for compute later, only regions with activity. Usually a pull reads one small manifest row.

### D3. Tighten-only merge, in the pack
The AI pack merges at lookup: release price, then shared price taking the higher of input and output separately, then the per-org `ai.prices` override, which wins as before because each org approved it. A model only in the shared table is floored at the release table's most expensive model of the same provider (the part of the model id before the first dot), or of the whole table if the provider is absent. The floor keeps a new model from tripping as unknown while making sure its spend is never estimated lower than the provider's dearest known model until a release prices it properly.

### D4. Shared prices are optional and fail closed to the release table
Shared prices live in the guard's state (DynamoDB, as one item per chunk, each under 400 KB thanks to the 1 MiB chunk cap compressing JSON well; a chunk too large for an item is kept gzipped). If they can't be read (no dataset, key without reach, Jennah down, corrupt chunk), the guard keeps the last good copy or uses the release table alone, and alerts once on the change in state. Since shared prices only raise or add, falling back to the release table never loosens anything.

### D5. A builder in the repo, publishing to Jennah
`internal/prices` builds a version from the AWS Price List API (`AmazonBedrock` and `AmazonBedrockFoundationModels`, us-east-1) joined with Bedrock's model list, matching on several normalized keys (name, model id, usage type), and reports models it couldn't match. `guardrail prices publish` runs it, shows the difference from the latest version (added, raised, lowered, removed), and publishes on confirmation. `--dry-run` only shows the difference. The same builder regenerates the embedded release table (`guardrail prices build -o`), so both share one method.

### D5a. One table per enterprise
`guardrail.prices` is per Jennah enterprise and shared by every MSP and payer org in it, since it holds AWS list prices that are the same for everyone. Where guards run in several enterprises (several distributors), each enterprise has its own table: `guardrail prices publish` acts on the active enterprise of the operator's Jennah login or key, prints which one, and is run once per enterprise. Enterprises stay isolated; no table is read across them. MSP-specific prices, if ever needed, would be an optional `guardrail.<msp>.prices` layered on top under the same tighten-only rule, which this change leaves out.

`prices` is reserved as an MSP id (`schema.ValidateMSPID` refuses it), so `guardrail.prices` can never be mistaken for an MSP's dataset prefix in listings or selectors.

### D6. Reader reach widens by one read-only dataset
The reader key's dataset selector adds `guardrail.prices`; its permissions are unchanged (data read applies to both). A reader key minted before this change keeps working for config and approvals; the guard detects the missing reach as a permission error on the prices read and alerts once, naming the fix (rotate the key with both datasets).

## Risks / Trade-offs

- [A price cut by AWS leaves guards over-estimating until the next release.] → Caps trip early, never late; a release carries the lower prices, and an org can approve lower `ai.prices` meanwhile.
- [The floor over-prices a cheap new model.] → It may cut off earlier than needed until a release; the org can approve an `ai.prices` entry for it.
- [Someone with write access to `guardrail.prices` can raise prices everywhere.] → That only tightens: it can cause early cutoffs, not overspend. Writes are limited to an ops key, and each guard records the version it applied.
- [Jennah's actual row and message limits differ from the assumed ones.] → Task 1.1 checks them before the chunk cap is fixed.

## Migration Plan

1. Release the guard with shared-price support; without the dataset or reach, it behaves as before.
2. Run `setup` once per enterprise to create `guardrail.prices`, then publish the first version.
3. Rotate each guard's reader key to include `guardrail.prices` (the documented rotation steps), at the next scheduled rotation or sooner.
